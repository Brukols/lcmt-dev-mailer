Forms can now take a file: a quote request with a logo or a brief, a job application with a CV. The file is attached to the email and never kept on the site. Fields in error also turn red as a whole, radio groups included.

## What changes

- **File fields.** Write `[brief file]` (optional) or `[brief* file]` (required) in an email template. The visitor picks one file, it arrives attached to the email, and the mail content shows its name. **Generate form template** writes the file input for you.
- **Formats and size per form.** Each template has a new **File uploads** row: tick the allowed formats (JPG/JPEG, PNG, WEBP, GIF, TIFF, PDF, AI, EPS, SVG; JPG, PNG and PDF by default) and set the maximum size in MB (10 by default). The row shows your server's own upload limit, and a larger value is lowered to it.
- **Real checks.** The server checks the size, the extension and the **content** of each file: a text file renamed `.pdf`, a PNG renamed `.jpg` or a script are refused with a clear message. The visitor's browser checks the format and size first, so they hear about it before sending.
- **Nothing kept on the site.** The file only exists for the time it takes to send the email, in a private temporary folder, and is deleted right after, sent or not. Received messages only keep the file name. A message blocked by the spam protection keeps no file, and **Send the email again** sends the email without the file: the message screen says so.
- **Fields in error turn red as a whole.** A field in error now also marks the label that wraps it and the legend of its group: a required radio group left empty shows its question in red, and the whole group clears as soon as the visitor picks an option.

## Security fixes

- **The signed-in account in emails can no longer be forged.** A visitor could post `currentUserEmail` and `currentUserLink` to the form endpoint and have their own values shown in the email instead of the signed-in account's (or pick the recipient when `[currentUserEmail]` was in **To**). Like `[submissionLanguage]`, these built-in placeholders are now always filled by the server; PHP calls of `Mailer::sendByKey()` can still pass their own values.
- **One solved ALTCHA challenge, one message.** Parallel requests replaying one solved challenge could all be accepted. The challenge is now claimed atomically before it is checked (`wp_cache_add()` with a persistent object cache, an `INSERT IGNORE` of its marker otherwise), so only one of them goes through.

## Updating

From the WordPress admin: Plugins → update "LCMT Mailer". Forms without a file field are not affected: they send exactly as before.

To add a file to a form: add `[name file]` to the template, check its **File uploads** row, then add the input to the theme's form file (see the README, *File fields*). If you use a page cache, purge it after updating so that pages load the new form script.

## For developers

- New placeholder type `file` (TypeScript type `File`). Forms with a file field post `multipart/form-data`, with `_context` as a JSON string; others still post JSON.
- Theme helpers: `lcmt_mailer_file_accept($key)` (the `accept` value), `lcmt_mailer_file_max_size($key)` (bytes) and `lcmt_mailer_file_hint($key)` (*Formats: JPG, PNG, PDF — 10 MB maximum*, translated). An element `[data-lcmt-file-name="<field>"]` shows the chosen file name and gets `data-lcmt-file-chosen`.
- New filters `lcmt_mailer_file_formats` (the format map: extensions and MIME types) and `lcmt_mailer_file_limits` (formats and size of one form, still capped to the server's limit).
- New post meta `_lcmt_mail_file_formats` and `_lcmt_mail_file_max_size`, copied to translations.
- `Mailer::sendByKey()`, `Mailer::sendWithBaseTemplate()` and `SubmissionRecorder::send()` take an optional list of attachment paths; existing calls keep working.
- `legend[aria-invalid="true"]` is now styled red like labels; style `[aria-invalid="true"]` to match.
